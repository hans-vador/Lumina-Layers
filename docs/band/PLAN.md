# Band mode (HueForge-style) adaptation plan

## diagnosis

WHY LUMINA DEFAULT OUTPUT HAS MANY FILAMENT CHANGES
- Colour model: every pixel gets an independent 5-layer stack ref_stacks[i] (index 0 = viewing surface, index 4 = next to backing) drawn from a measured LUT of 1024 (4C) / 1296 (6C) / 2738 (8C) mixed colours (core/image_processing.py:218-487). Verified: in the 4C set every layer position takes all 4 materials; in assets/smart_8color_stacks.npy every column uses all 8 IDs. _build_voxel_matrix (core/converter.py:2150-2212) puts material_matrix[:,:,z] at Z=z, so every optical Z layer is a mosaic of up to N materials.
- Meshing: one trimesh per material slot (converter.py:1113-1157, HighFidelityMesher core/mesh_generators.py:198-298 with 1-px dilation at 388-407) -> one 3MF part per filament with extruder=idx (utils/bambu_3mf_writer.py:406-413). Bambu Studio therefore tool-changes every time a layer contains >1 part: changes ~= sum_z (m_z - 1) + layer-boundary transitions. RYBW single-sided: 5 layers x 3 = 15 (+1 into backing); UI default Double-sided (ui/layout_new.py:2323, converter.py:2177-2192): ~31; 8-Color: ~35 / ~72. Writer forces enable_prime_tower='1' and single_extruder_multi_material='1' (bambu_3mf_writer.py:571-572) with an H2D template (bambu_config_template.json: prime_tower_width 230, wipe_tower 80,250, printer 'Bambu Lab H2D', wall_loops 1, top/bottom shell 0) -> a wipe tower purge at every change. No mechanism anywhere imposes a global filament-per-layer order; the only per-layer constraint is 5-Color Extended's '<=4 materials per Z' (converter.py:986-998, 2249-2250).
- Orientation: face-down (viewing surface printed first on the bed, Z=0), X-mirrored for single-sided (converter.py:1401-1411). References are face-up.

WHAT 'LUMINA QUALITY' ACTUALLY COMES FROM: large mixed-colour gamut (1024-2738 measured colours), 10 px/mm raster, bilateral(d=9, sigma 10) + K-Means(48) + Lab-KDTree nearest neighbour (image_processing.py:680-834), isolated-pixel cleanup, glossy squished first layer as the viewing face, full 0.4 mm opaque stack over white. Its cost is precisely the per-layer material mosaic (many changes, prime tower, 4 overlapping meshes of 2-3M tris each). It has NO dithering, matches in OpenCV-scaled Lab (L x2.55), and produces posterised bands.

WHAT THE REFERENCES DO (scratchpad REF_ASTRO / REF_GRAD, verified files):
- ONE watertight continuous heightfield solid per plate, single part, object extruder=1 (Metadata/model_settings.config: <object id=2><metadata key=extruder value=1/><part id=1 subtype=normal_part>...). Mesh z is continuous (only ~11% of vertices near a 0.08 grid), top surface 94-97% sloped triangles; XY pitch ~0.11 mm local (200 mm mesh scaled 0.66665 -> 133.33 mm printed).
- Colour by plate-wide swaps: Metadata/custom_gcode_per_layer.xml with <layer top_z=.. type="2" extruder=".." color="#.." extra="" gcode="tool_change"/> x3 and <mode value="MultiAsSingle"/>. Astro: 0.88->ext2 #C12E1F, 1.20->ext3 #FF9016, 1.68->ext4 #FFFFFF (FL 0.16: top_z(n)=0.16+0.08(n-1) -> layers 10/14/20). Grad: 0.92->ext3, 1.08->ext4, 1.32->ext2 (FL 0.2, extruder order not monotonic). EXACTLY 3 changes for the whole print, enable_prime_tower 0, no wipe tower.
- Thin translucent bands (Red 4 layers, Orange 6, White 8; Grad Purple 2, Pink 3): each 0.08 layer inside a band is a distinct tint of that filament over the darker one below -> ~19-22 usable tones from 4 filaments. Base band ~9 layers (0.80-0.84 mm) of the darkest filament; HueForge 'Base Thickness 0.48' = minimum column height (relief 0.52-2.24 mm); max 2.24 mm = 27 layers.
- Top-surface area is spread over all ~22 tonal layers (Astro borderless L6..L27 each 1-10%), no bimodality. Dark filament first, light last.
- Profile: layer_height 0.08, initial_layer_print_height 0.16 (Astro) / 0.2 (Grad), wall_loops 2, top/bottom_shell_layers 9999 (Astro) or 9/7 (Grad), sparse_infill_density 100% zig-zag, top_surface_pattern monotonicline, no ironing, elefant_foot 0.075-0.15, seam aligned, wall_generator classic, flush_into_support 1, filament 'Bambu PLA Basic'. Description text lists TDs: Black 0.2, Indigo Purple 1.1, Pink 8, Jade White 5 (HueForge units, mm).

THE USER'S OWN ATTEMPT (Downloads/BambuAlbums/*.3mf, built by tools/rebuild3.py) already uses the right physics idea but: 4 stacked slab PARTS with per-part extruder (colour-by-part instead of custom gcode), heights fitted on a 0.02 grid then gaussian-smoothed, 450 px grid (0.334 mm pitch, coarser than 0.42 nozzle-limited reference at 0.075), luminance-weighted RGB fit with rebuild3 TD table (0.35-0.7 mm, exp(-t/td)) -> 66% of surface in the white band, 0% black-top (bimodal), and a stale profile (layer_height 0.2, prime tower on, filament arrays of inconsistent lengths 3/4/18).

CONCLUSION: reference parity requires the HueForge output MODEL (continuous heightfield + MultiAsSingle plate swaps + fine profile), not Lumina's per-pixel stack model. Lumina's measured 5-layer LUTs are physically inapplicable (face-down, always over white, each layer any material) and none exists for these 12 filaments anyway. What IS reusable from Lumina: image loading/filtering/quantising/Lab-KDTree matching (unchanged, via a ramp LUT saved in Lumina's .npz {rgb,stacks} format), isolated-pixel cleanup, LUT persistence/discovery, the streaming 3MF writer (extended), naming, and the Gradio/API plumbing if wanted.

## lut_strategy

GOAL: for a BandSchedule, obtain colour(k) for k = n0..K layers (about 19 rows). Three sources, in a common container (ramp LUT .npz {rgb (K',3) uint8, stacks (K',5) int32} + sidecar json) so BandProcessor never knows which produced it.

A) EXISTING LUMINA PRESETS: not transferable. Reasons (verified): (1) physics — presets are face-down 5-layer stacks over a 1.6 mm white backing with any material at any layer; band physics is face-up, dark base, thin light bands. (2) Orientation — the LUT 'viewing surface' is the squished first layer on the plate; measured wedges show near-total opacity at 1 layer: lut-npy预设/bambulab/Bambulab&PLA&4色&RYBW&红-蓝-黄-白.npy rows R^m W^(5-m) (index = base-4 digits MSB=viewing): m=1..5 -> (205,85,61),(201,70,55),(228,83,73),(215,69,65),(207,71,69) => o(1 layer)~0.99, TD_eff(k=3)~0.05 mm; Y same; B (86,118,181),(48,72,161),(44,63,169),(53,64,154),(25,33,128) => o1~0.83; Custom/Bambulab&PLA&8色 (smart_8color rows 11/43/236/1077 = R^m W^(5-m)) gives R (233,115,88)->(217,67,57) o1~0.93; DB rows 12/51/279/1223 o1~0.75; G rows 13/59/327/1353 o1~0.72. Conversely W^4 over R = #B98982 => o_W(0.32 mm)~0.45 => TD_W_eff~1.6 mm (k=3) vs HueForge library 5. These numbers are camera-relative (auto WB from corner patches, no ICC) and first-layer-biased; use them ONLY as a sanity envelope ('saturated colours reach >90% in 1-2 face-up layers is plausible; white ramps over ~0.3-0.6 mm'). (3) Coverage — only Black, White, Red #C12E1F, Green #00AE42 (and probably Yellow) of the user's 12 correspond to Bambu presets; Klein Blue #1E44BE != Bambu Blue #0A2989; Coffee Brown, Sunny Orange, Oak, Lavender, Pink, Beige have no LUT. Also bambulab/Bambulab&PLA&8色-New.npy pure rows are hand-edited nominal hex, and Custom/Bambulab&PLA&RYBW is byte-identical to the generic/Elegoo file (pure white #C3D6E8) -> not Bambu data.

B) SYNTHETIC OPTICAL MODEL (default until calibrated): assets/filaments_user.json = 12 entries {name, hex, td_mm, td_source}. Composite in linear RGB, bottom-up: C = rgb_lin(base); for band b=1..B-1 with thickness t_b = lh*stacks[k][b]: o_b = 1 - exp(-k_opaque * t_b / TD_b) (k_opaque=3.0 => 95% opaque at t=TD; expose k_opaque and allow 'linear' o=min(1,t/TD)); C = C*(1-o_b) + rgb_lin_b*o_b; sRGB-encode -> uint8. (rebuild3.comp L81-88 is the same recurrence with k=1; Lumina's calibration.py:225-240 / 769-781 alpha=min(1,0.08/(td/10)) is a per-layer linear variant with td in 0.1 mm units — do not reuse its constants.) TD inputs, in priority: (i) HueForge filament library values for the exact Bambu SKUs (anchors visible in REF_GRAD description: Black 0.2, Indigo Purple 1.1, Pink 8, Jade White 5; user's own HueForge-Covers README assumed 'TD ~1 mm colours, ~1.8 mm white'); (ii) rebuild3 TD table (Downloads/BambuAlbums/tools/rebuild3.py:23-25: K .35, W .5, brown .55, blue .55, red .55, green .55, orange .55, oak .6, lavender .6, pink .6, beige .6, yellow .7 — but those are for exp(-t/td), i.e. multiply by ~3 for k_opaque=3) flagged td_source='guess'. Trade-off: zero prints, unvalidated tonal spacing; wrong TD mostly shifts where a band saturates (too-thin band = lost tones; too-thick = wasted layers). Mitigation built in: band thicknesses come from the optimiser, and swap heights are trivially nudged by +-1 layer in Bambu Studio after a test print.

C) CALIBRATION (drop-in, two levels):
 C1 Schedule-specific ramp board (exact measured LUT, one small print, B-1 swaps): core/band/calibration.generate_ramp_board(schedule, filaments): single heightfield object, K-n0+1 (+engraving rows optional) 5x5 mm columns at heights h_k, 0.8 mm gaps, 1-cell border + corner markers like calibration.generate_calibration_board (core/calibration.py:86-198) but exported through export_band_3mf (same custom gcode swaps, same profile). Photograph -> extract_ramp_board(img, 4 corners, grid rows x cols) reusing core/extractor.py warp (L219-227), apply_auto_white_balance (L229-230), 8x8 mean sampling (L267-271) via a new grid branch (L187-214 currently hard-codes 6/32/36/37/38) -> rgb (K',3) -> save Custom/Band_<key>_measured.npz with identical stacks -> MeasuredRampModel. ~20 min print, exact colours for that palette/order/thickness; must be reprinted if thickness changes (cheap).
 C2 General TD wedge boards (fits the synthetic model for ANY schedule): generate_td_wedge_board(filaments<=3, base='Black' then 'White'): black base 10 layers + per-filament columns of 1..12 layers; because a heightfield cannot skip layers, use the legacy per-part-extruder writer for this board only (3 parts on layers 11-22 => <=3 changes/layer x 12 layers, acceptable for a 60x30 mm board). fit_td(colors, full, base): o_m = dot(lin(c_m)-lin(base), d)/|d|^2, d = lin(full)-lin(base); TD = -k_opaque*m*lh/ln(1-o_m) averaged over m with 0.05<o_m<0.95 -> writes td_mm, td_source='fitted' into filaments_user.json. 12 filaments = 4-5 boards.
Code structure for drop-in: OpticalModel protocol; ramp_lut.build_ramp_lut(schedule, model) is the only producer; MeasuredRampModel loads by schedule.key(); pipeline picks measured npz automatically if present in lut-npy预设/Custom/, else BeerLambert(filaments_user.json), and records the source in the 3MF Description and stats.

## palette_method

INPUT: per album, hist = image_hist_lab(image_path, k=64): resize to 256x256 (LANCZOS), sRGB->linear->true CIELAB D65, cv2.kmeans(k=64, KMEANS_PP_CENTERS) -> centres c_j (Lab), weights w_j = n_j/sum (optionally multiplied by a centre-weighted saliency window). For a GLOBAL palette, concatenate the per-album (c_j, w_j/n_albums) sets.

CANDIDATE: ordered 5-subset of the 12 filaments (bottom->top: f0 base, f1..f4 bands) + thickness vector n=(n1..n4), n_i in [1,8], with base n0 fixed (default 9 layers => first swap at layer 10 = 0.88 mm with FL 0.16, as both references) and total K = n0+sum(n_i) <= 27 (2.24 mm). Ramp colours r_k, k=n0..K, from OpticalModel (K-n0+1 <= 19 tones).

COST(S) = sum_j w_j * min_k dE(c_j, r_k) with dE = sqrt(wL*dL^2 + da^2 + db^2), wL default 1.5 (album art is luminance-dominant and a 1-D ramp cannot match hue everywhere), optional final re-rank of the top 20 with vectorised CIEDE2000; + lambda_K*K (print-time regulariser, lambda_K=0.05 dE per layer) + penalty 5 dE for any band that receives < 0.5% of pixels (encourages dropping to 4 filaments = one fewer swap). 4-filament schedules are evaluated alongside; pick 4 if cost4 <= 1.05*cost5.

SEARCH (two stage, vectorised numpy):
 Stage 1 — subsets: 792 = C(12,5) (plus 495 4-subsets). Order by luminance ascending (Y of rgb_lin) — the reference convention; evaluate three canonical thickness vectors (3,4,6,8),(4,4,4,6),(2,3,5,8) -> keep top 12 subsets.
 Stage 2 — for each kept subset: all 120 orders (or the 12 orders with base in the 2 darkest and top in the 2 lightest when time-limited) x all n in [1..8]^4 with sum<=18 (~2500) -> ~3.6M schedules x <=19 ramp colours x 64 hist colours ~ 4.4e9 float ops, chunked; ~30-60 s on the .venv (numpy 2.4). Ramp composition is vectorised over (n-vectors, k): t_b(k) = lh*clip(k - c_{b-1}, 0, n_b).
 Output: BandSchedule + report (per-band pixel share, predicted mean dE, coverage of the darkest/lightest 5% of pixels).
GLOBAL vs PER-ALBUM: filament ORDER must be global to avoid re-spooling (AMS holds the 5 in slots 1-5 = extruder indices), but band THICKNESSES are per-print (swap heights live in custom_gcode_per_layer.xml), so select_global_order(hists) fixes (subset, order) over all albums and optimise n per album with the fixed order (Stage 2 only, 2500 evals, <1 s). Store chosen schedules in output/<album>_band_schedule.json and print human swap instructions ('Start Black; at layer 10 (0.88 mm) swap to Red; ...') into the 3MF Description like HueForge.
Notes: colours with |a|,|b| far outside the ramp (e.g. saturated cyan on a warm palette) will map to the nearest luminance — expected HueForge behaviour; report the residual so the user can pick a different 5-subset manually (CLI --palette 'Black,Klein Blue,Red,Sunny Orange,White' --order fixed).

## change_reduction

MECHANISM: replace per-pixel material stacks with a global layer schedule and encode colour by plate-wide swaps, exactly as the references. Geometry becomes ONE single-material heightfield solid (extruder 1); colour comes from Metadata/custom_gcode_per_layer.xml (type=2 tool_change, MultiAsSingle). Tool changes are then independent of image content and size.

MATH
- Layer numbering (Bambu): layer n (1-based) has top z_n = FL + lh*(n-1), FL = initial_layer_print_height (0.16), lh = 0.08. A column of height h contains layer n iff h > z_n - lh/2 (n>=2; layer 1 iff h > FL/2). Ramp LUT height for k layers: h_k = z_k (mid-cell => robust to float error).
- Schedule: bands b=0..B-1 with n_b layers, c_b = sum_{j<=b} n_j, K = c_{B-1}. Band b (b>=1) starts at layer s_b = c_{b-1}+1; swap entry top_z = z_{s_b} = FL + lh*c_{b-1}, extruder = b+1 (1-based, = filament index), color = hex_b. Check against reference: FL 0.16, n0=9,n1=4,n2=6 -> top_z 0.88, 1.20, 1.68 = REF_ASTRO exactly.
- Tool changes per print = B-1 (4 for 5 filaments, 3 if optimiser picks 4), each a single AMS swap + purge; no wipe tower (enable_prime_tower 0). Versus Lumina default: RYBW single-sided ~16, double-sided (UI default) ~31, 8C ~35-72, all with a 230 mm prime tower. Reduction >= 4x (single 4C) to 8x (default double-sided), and purge count equals change count.
- Usable tones = K - n0 + 1 (19 for K=27,n0=9) + geometric anti-aliasing: pixel height h = z_k + lh*f, f in [-0.5,0.5), stays in layer k's slice cell but the triangulated surface between neighbouring pixels crosses the slice plane z_k + lh/2 at a sub-pixel XY position, so tonal boundaries land between pixels (the reference's 'continuous z / 94% sloped triangles' behaviour) — not achievable with Lumina's stepped voxel boxes.
- Engraving (optional, HueForge-like base relief): pixels matched to the base tone (k=n0) get h = z_{n_min} + (z_{n0} - z_{n_min}) * clip(L*/L*_base, 0, 1), n_min = 5 (0.48 mm): same colour, added depth; no extra changes.

INSIDE THE LUMINA FRAMEWORK: the ramp LUT is a legal Lumina .npz (rgb (K',3), stacks (K',5)) so LuminaImageProcessor produces material_matrix whose entries are per-band layer counts; the constraint 'one filament per Z layer' is therefore enforced by construction of the candidate set (all rows share the same filament at each z), which is the same lever the algorithm report identified (filter candidates before the KDTree at core/image_processing.py:479) taken to its limit, with per-pixel HEIGHT restoring the degrees of freedom the strict filter removes. The voxel builder and per-material mesher are not used; changes cannot re-appear downstream because there is exactly one part.

OPTION B (rejected, documented for completeness): keep Lumina stacks but filter (lut_rgb, ref_stacks) at image_processing.py:479 (and before the early returns at L238-239/L360-361) to rows with ref_stacks[i][z] in A_z = {order[z], base}: changes <= 2 per optical layer => <= 2L+1 = 11 single-sided; palette collapses to |prod A_z| = 32 stacks of which the measured LUT covers only those present for the chosen filaments; no measured LUT exists for the user's spools; output stays face-down, stepped, with a prime tower — not reference quality.
